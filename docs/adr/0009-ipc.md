# ADR 0009: IPC: endpoints, call/reply, notifications, capability transfer, fault IPC

Status: accepted

Refines ADR 0003, step 5. This is the specification; nothing in step 5 is
implemented until it is agreed. Rule numbers (P1..P37, with P6a, P23a and P27a) are referenced from
`docs/SECURITY.md`.

IPC is where authority starts to move between tasks. Every rule below
serves one of three goals:

1. **No authority appears or moves without explicit permission**, and none
   is duplicated by accident.
2. **Every operation is atomic:** it commits completely or changes nothing
   observable.
3. **No thread is ever blocked on, or linked to, something that no longer
   exists**, and no structure ever points at a dead thread.

## Scope

In scope, and nothing else:
- synchronous endpoints: `send`, `call`, `recv`, `reply`, `reply_recv`
- notifications: `signal`, `wait`, `poll`
- capability transfer in messages
- fault delivery to a handler endpoint
- the thread states and queues these need

Explicitly **out of scope** for this step:
- **Asynchronous message queues of any kind.** The only buffering in the
  kernel is the single message staged in each blocked sender's own TCB.
- Non-blocking send variants, timeouts, and a direct-switch fast path.
  These are performance features to add after measurement.
- Unwrapping badged endpoint capabilities sent to their own endpoint
  (ADR 0003). Until then, a server that receives a copy of its own badged
  capability identifies it with `cap_identify`.
- Moving (rather than copying) capabilities, and reply objects that a
  server can hand to another thread (needed for deferred replies; MCS-
  style, later).
- Priorities and timer preemption (step 6). **T36 still gates untrusted
  code.**

## Objects

| Object | Size | Contents (kernel memory, never user-visible) |
|---|---|---|
| `Endpoint` | 64 B (exists) | send queue (head, tail), receive queue (head, tail), count of capabilities with SEND, count with RECV |
| `Notification` | 64 B (new) | pending bit word, wait queue (head, tail), count of capabilities with WRITE |

Both are retyped from Untyped like everything else (O3). Queues are
intrusive: every thread has **one** wait link in its TCB, because a thread
blocks on at most one object at a time. **IPC never allocates.**

## Rights

| Capability | Right | Allows |
|---|---|---|
| Endpoint | WRITE ("send") | `send`, `call` |
| Endpoint | READ ("receive") | `recv`, `reply_recv` |
| Endpoint | GRANT | transferring capabilities in a message sent with this capability, and receiving capabilities in the reply to a `call` made with it (recorded at call time, P23a) |
| Notification | WRITE | `signal` |
| Notification | READ | `wait`, `poll` |

**P1. Badges.** Endpoint and notification capabilities may carry a badge,
set once at derivation. The rule is explicit:
- A capability derived from a **badged** capability carries exactly that
  badge. Asking for a different one is `T_EPERM`.
- Only an **unbadged** capability can mint a badged copy (and unbadged
  copies of it can mint too).

A receiver learns the badge of the capability the sender used. A
notification signal sets exactly the bits of the badge of the capability
used (P20). An unbadged notification capability is minting authority,
not signalling authority.

## Message format

**P2. A message is:**
- a 32-bit label
- up to `MSG_MAX_WORDS` = **32** data words (256 bytes)
- up to `MSG_MAX_CAPS` = **3** capability slots

**P3. The info word** carries the shape of a message in a register:

| Bits | Field |
|---|---|
| 0–5 | length in words (0..32) |
| 6–7 | number of capabilities (0..3) |
| 8–31 | must be zero on input; on output, bits 8–9 report capabilities delivered and bit 10 reports a skipped reply (P19) |
| 32–63 | label |

Reserved bits set, length > 32 or more than 3 capabilities: `T_EINVAL`.

**P4. Data and capability slots travel in the thread's IPC buffer,** a
Frame bound in `TS_IPCBUF`. The kernel reads and writes it only through the bound frame's physical
address, after the binding has established the frame's authority and its
W^X constraints (P5). **IPC performs no user-virtual-address
dereferences.** It does access memory a user task owns, which is why the
binding rules matter.

A buffer is required to send (or reply with) any data words or
capabilities, and to receive at all. A message with length 0 and no
capabilities (label and badge only) can be sent without one. Missing
buffer: `T_EINVAL`.

```c

struct ipc_buffer {               /* fixed layout, no padding */
    uint64_t words[32];           /* message data */
    uint32_t caps[3];             /* send: slots of capabilities to transfer */
    uint32_t recv_slots[3];       /* receive: empty slots for incoming caps */
    uint32_t recv_count;          /* how many recv_slots are offered (0..3) */
    uint32_t reserved;            /* must be zero */
};
```

**P5. An IPC buffer is a writable alias.** Because the kernel writes into
it, binding a Frame as an IPC buffer counts as a writable mapping for
the W^X alias rule (ADR 0007, V6):
- binding fails if the frame is mapped executable anywhere
- mapping it executable fails while it is bound

Binding requires READ and WRITE on the frame capability, besides GRANT
(T1).

**P6. Messages are captured once, at send time.** The sender's label,
length, data words and capability slot numbers are copied from its IPC
buffer into a staging area in its own TCB when it sends, and are validated
there (T21/T27 for IPC). Nothing is read from the sender's IPC buffer
afterwards. A blocked sender's message therefore cannot change while it
waits, even if another thread writes to the buffer.

**P6a. When an IPC buffer is required.** Because of P6, a sender's buffer
stops mattering once its message is captured. Receive slots are numbers
captured once as well (P24), but delivery writes words into the
receiver's buffer, so receiving needs one.

| Thread | IPC buffer required? |
|---|---|
| RUNNING, issuing `send`/`call`/`reply` with data or capabilities | Yes, to capture the message |
| RUNNING, issuing a message with length 0 and no capabilities | No |
| `BLOCKED_SEND` | **No**: the message is already captured |
| `BLOCKED_RECV` | Yes |
| `BLOCKED_REPLY` | Only if the reply that arrives carries data or capabilities |
| `BLOCKED_NOTIF` | No |

Losing `TS_IPCBUF` aborts a thread only when the table says it is
required: a `BLOCKED_RECV` thread is aborted (P30). For a `BLOCKED_REPLY`
thread, a reply that carries a payload fails validation instead (P18),
and the server keeps its reply authority.

**P7. Messages carry no kernel pointers.** What a receiver gets:
- the label and data words, exactly as the sender wrote them
- the badge of the sender's capability
- the receive slots its new capabilities landed in

Kernel structures never enter a message. The staging area is zero-filled
beyond the message length, so no stale data from earlier messages leaks.

**P8. Delivery.**
- The receiver's IPC buffer gets `words[0..length)`.
- RSI gets the info word (bits 8–9: capabilities delivered).
- RDI gets the badge.
- RAX gets 0.

The rest of the IPC buffer is not touched. This extends T20: IPC syscalls
return values in RSI and RDI in addition to RAX.

## Thread states and queues

New states, added to those of ADR 0008:

| State | Where the thread is | Waiting for |
|---|---|---|
| `BLOCKED_SEND` | an endpoint's send queue | a receiver (`send`, `call`, or fault delivery) |
| `BLOCKED_RECV` | an endpoint's receive queue | a sender |
| `BLOCKED_REPLY` | no queue; linked to exactly one server thread | that server's reply |
| `BLOCKED_NOTIF` | a notification's wait queue | a signal |

**P9. Structural invariants**, checked by an audit function after every
IPC test step:
1. A thread is on the run queue **iff** it is RUNNABLE.
2. It is on an endpoint queue **iff** it is `BLOCKED_SEND` or `BLOCKED_RECV`
   on that endpoint, and in the queue matching its state.
3. It is on a notification queue **iff** it is `BLOCKED_NOTIF` on it.
4. It is `BLOCKED_REPLY` **iff** exactly one server thread's reply link
   points to it and its own link points back.
5. A thread is on at most one queue of any kind.
6. A thread is RUNNING **iff** it is the CPU's current thread.
7. Every queue link, reply link and wait-object pointer refers to a live
   object; queues are well-formed doubly linked lists.

**P10. Blocked means not runnable.** Every transition into a BLOCKED
state removes the thread from the run queue (it was RUNNING, so it is not
on it) and makes it non-current before the syscall returns to the
scheduler. Every wake-up:
- writes the result registers (P8)
- sets the state to RUNNABLE
- appends the thread to the run queue

All three happen together. The thread was blocked inside a syscall it
entered with SYSCALL, and only RAX, RSI and RDI change, so its return path
stays as ADR 0008 T18 decided.

### Transitions

| From | Event | To | Effect |
|---|---|---|---|
| RUNNING | `send` / `call`, receiver waiting | RUNNING (`send`) or BLOCKED_REPLY (`call`) | message delivered; receiver RUNNABLE; for `call`, server's reply link set |
| RUNNING | `send` / `call`, no receiver | BLOCKED_SEND | appended to send queue (the call flag is recorded) |
| RUNNING | `recv`, sender queued | RUNNING | message delivered from the queue head; sender RUNNABLE (`send`) or BLOCKED_REPLY (`call`) |
| RUNNING | `recv`, no sender | BLOCKED_RECV | appended to receive queue |
| BLOCKED_SEND | a receiver arrives | RUNNABLE or BLOCKED_REPLY | as above |
| BLOCKED_RECV | a sender arrives | RUNNABLE | message delivered |
| BLOCKED_REPLY | the server replies | RUNNABLE | reply delivered |
| RUNNING | `wait`, no bits pending | BLOCKED_NOTIF | appended to wait queue |
| BLOCKED_NOTIF | a signal arrives | RUNNABLE | bits delivered (P21) |
| any BLOCKED | `thread_suspend`, losing a required binding (T2), or losing `TS_IPCBUF` while it is needed | INACTIVE | IPC aborted (P30); on a later resume the syscall returns `T_EINTR` |
| any BLOCKED | the object or peer is destroyed, or the last opposite-direction capability is deleted | RUNNABLE with `T_EDEAD` | P26–P29 |
| any | last Thread capability deleted | destroyed | P31 |

**P11. Queues are FIFO.** Senders are served in arrival order, and so are
receivers and notification waiters.

**P12. Who runs next.** A woken thread is appended to the run queue; the
current thread continues unless it blocked. There is no direct switch yet,
so the order is deterministic and testable.

## Endpoints

**P13. `send(ep, info)`** needs WRITE on `ep`.
- If a receiver is queued, the message is delivered (P8) and both
  continue.
- Otherwise the sender blocks in `BLOCKED_SEND` until a receiver comes.

**P14. `call(ep, info)`** needs WRITE on `ep`. It is a `send` followed,
atomically at delivery, by `BLOCKED_REPLY`. The receiving thread gets the
**reply authority** for this caller (P16).

**P15. `recv(ep)`** needs READ on `ep`, a bound IPC buffer, and **no reply
authority currently held** (`T_EBUSY` otherwise; P17).
- If a sender is queued, its staged message is delivered.
- Otherwise the receiver blocks in `BLOCKED_RECV`.

### Rendezvous rules (step 5.3)

These refine P13 and P15 for data-only messages. They are what the
endpoint tests and the structural audit check.

**P38. Never both queues.** An endpoint never has a waiting sender and a
waiting receiver at the same time: whoever arrives second rendezvouses
instead of queueing.

**P39. FIFO.** Each queue is served strictly in arrival order. With
senders S1, S2, S3 and receivers R1, R2, R3, every arrival order pairs
S_i with R_i.

**P40. One queue per thread.** A thread is in at most one wait queue, its
state is that queue's kind, and the queue's links agree with it (P9).

**P41. One pair per rendezvous.** A rendezvous removes exactly one sender
and one receiver, the head of each side. The waiting partner leaves its
queue, has its result set and becomes RUNNABLE in one step (P10). The
arriving partner continues.

**P42. Nothing is left behind.** A staged message exists only while its
thread is BLOCKED_SEND. Leaving the send queue by any route (rendezvous,
`T_EDEAD`, suspension, destruction) erases it, and nothing beyond the
message length is ever stored.

**P43. Last receive authority.** When the last capability with READ on
an endpoint is deleted, every blocked sender wakes with `T_EDEAD`. A
blocked sender waits for a receiver, so only receive authority keeps it
alive. Deleting send capabilities, its own included, does not wake it.

**P44. Last send authority.** When the last capability with WRITE is
deleted, every blocked receiver wakes with `T_EDEAD`. Deleting a master
or root capability wakes nobody while another live capability still
carries the authority (P27a). A new `send` with no READ anywhere, or
`recv` with no WRITE anywhere, fails at once with `T_EDEAD` instead of
blocking forever.

**P45. Semantic counts.** P43 and P44 use the P27a counts, excluding
the capability being deleted.

**P46. Captured at send time.** A sender that blocks has its message
copied into its TCB before it blocks. Rewriting or unbinding its IPC
buffer afterwards does not change what is delivered (P6, P6a).

**P47. Validate, then commit.** Every check (rights, message shape,
buffers, reply authority, liveness) passes before any queue is touched.
A refused operation leaves the queues, every thread's state, result,
registers and staged message, and the run queue exactly as they were.

**P48. Exact delivery.** The receiver gets exactly `length` words in its
IPC buffer, the info word in RSI and 0 in RDI (no badges in step 5.3).
Nothing else in the buffer, and none of the sender's registers, is
written.

### Reply authority

**P16. Reply authority is not a capability.** It is per-thread kernel
state in the server's TCB: a link to the one caller it may answer, and
the caller's link back. It lives in no cspace and has no slot number, so
it cannot be copied, transferred, derived or confused with an endpoint
capability. `reply` takes **no target argument**: it can only answer the
server's own pending caller.

**P17. At most one outstanding reply authority per server thread.**
- A server holding one cannot `recv` (`T_EBUSY`); it must `reply` or
  `reply_recv` first.
- A caller is linked to at most one server.
- Reply authority is single-use: it is consumed when the reply is
  delivered or the caller is found gone, and never otherwise (a reply
  that fails validation keeps it, P18).

**P18. `reply(info)` follows exactly the rules of a send** (P3–P8, P23–P25,
P36):
1. It captures the reply message from the server's IPC buffer once.
2. It validates the reply against the caller's captured receive slots and
   `call_grant`.
3. It commits.

Outcomes:
- **Delivered:** the caller was still `BLOCKED_REPLY`; it gets the message
  (P8) and becomes RUNNABLE, and the reply authority is consumed.
- **Caller gone:** the caller was destroyed or its call aborted. `reply`
  returns `T_EDEAD`, the authority is consumed, and nothing else changes.
- **Validation failed:** a bad message; capabilities without
  `call_grant`; or a caller without a buffer or with too few or
  now-occupied receive slots. `reply` returns the error, **the authority
  is kept**, and nothing changes. The server can retry, for example with
  a zero-length reply.
- **No reply authority:** `T_EINVAL`.

**P19. `reply_recv(ep, info)` is one atomic operation, not a `reply`
followed by a `recv`:**
1. Capture and validate the reply (P18), if reply authority is held.
2. Validate the receive half: READ on `ep`, a bound IPC buffer, valid
   receive slots.
3. Only then commit the reply and consume the authority.
4. Then receive. That may block, which is a normal outcome, not a
   failure.

If either half fails validation, nothing has changed: no reply was
delivered, the authority is kept, and the error is returned. If the
caller had gone, the reply part is skipped, the authority consumed, and
bit 10 of the returned info word reports it. Afterwards RAX/RSI/RDI hold
the receive's result.

### Call and reply rules (step 5.5)

These refine P8, P14-P19, P23a and P28-P31. They add no new kind of
authority: a call is a send that leaves reply authority behind, and a
reply is a send to exactly one thread, checked and committed with the
same plan as P49-P56.

**P57. Badges.** A message delivered by `send` or `call` carries, in
RDI, the badge of the endpoint capability the sender used (0 if it is
unbadged). The badge is captured with the message at the time of the
`send` or `call`, like the GRANT check (P51), so deleting that
capability later does not change it. A reply delivers 0 in RDI.

**P58. `call(ep, info)`** is `send` (P13, P51) plus:
- **The caller's offer.** If the caller has an IPC buffer, its receive
  offer for the reply is captured and validated at the call (P50). A
  caller without a buffer offers nothing and can receive only a
  label-only reply.
- **`call_grant`.** The caller records whether the endpoint capability
  it used has GRANT, at the call (P23a).
- **Rendezvous.** In the same step that delivers the message, the
  receiver gets reply authority for this caller (PENDING, with
  `call_grant`), and the caller goes straight to BLOCKED_REPLY. It is
  never RUNNABLE in between.

A queued caller holds its message, offer and call flags in its TCB.

**P59. Staged state lifetime** (extends P42 and P50):
- a message, only while BLOCKED_SEND
- an offer, only while BLOCKED_RECV, BLOCKED_REPLY, or BLOCKED_SEND as
  a caller
- the call flags, only while BLOCKED_SEND
- the skipped-reply flag (P63), only while BLOCKED_RECV

All of it is erased whenever a thread leaves IPC: it is woken, aborted
or destroyed. A caller's move from BLOCKED_SEND to BLOCKED_REPLY keeps
only its offer.

**P60. Reply authority and its holder.** A thread in BLOCKED_RECV never
holds reply authority, because `recv` refuses (P17). `reply_flags` is
nonzero only while the authority is PENDING. The audit checks both.

**P61. `reply(info)`** never blocks. It checks, in this order:
1. No reply authority: `T_EINVAL`.
2. Caller gone (P29): the authority is consumed, `T_EDEAD`, and nothing
   else changes. The message is not examined: there is no one to send
   it to.
3. Otherwise the reply is checked like a send to the caller:
   - the message shape (P3)
   - the server's buffer if the reply carries data or capabilities (P4)
   - `call_grant` if it carries capabilities (`T_EPERM`)
   - the server's listed capabilities (P51)
   - the caller's buffer if the reply carries data (`T_EINVAL`)
   - fit against the caller's offer captured at the call (P52)

   Any failure returns the error and **keeps the authority**; nothing
   changes (P18).
4. Commit, in one step: transfer, deliver (RDI 0), consume the
   authority, and make the caller RUNNABLE.

**P62. Reply authority can never be named.** It has no capability
type, no slot and no object. `reply` takes no target, and `reply_recv`
names only the endpoint to receive on.

**P63. `reply_recv(ep, info)`** runs in phases. Nothing of the
server's own state changes before phase 5:
1. **The receive half:** READ on `ep`, an IPC buffer, and the server's
   own offer (P50).
2. **The reply half,** if the authority is PENDING: everything in P61
   step 3. In addition, the reply's destination slots must not be slots
   of the server's own offer (`T_EBUSY`). This can only happen when the
   caller and the server share a cspace, and without the rule the
   reply's commit could fill a slot the receive has already validated.
3. **Drain:** queued senders that cannot be delivered into the server's
   offer are failed, as in any receive (P53). That is their own
   outcome, not a change to the server's state.
4. **Liveness:** if no deliverable sender is queued and no WRITE
   capability exists, `T_EDEAD`. Nothing of the server's has changed,
   and the authority is kept.
5. **Commit the reply** (P61 step 4), or consume an authority whose
   caller is gone. Then the receive either takes the head sender, which
   was validated in phase 3 and cannot have been invalidated by the
   reply's commit, or blocks.

**All destination slots of both halves are validated against the
server's current cspace before either half commits.**

With no reply authority, `reply_recv` is a receive. The skipped-reply
bit (bit 10) belongs to the **receive**, not the reply: when a
caller-gone authority is consumed, the bit is committed together with
the receive transition. It is written into RSI in the same step that
delivers the receive's message, either at once or later if the receive
blocked first. It is erased with the receiver's other staged state if
the receive ends any other way (P59), and such a receive reports only
its error.

**P64. Aborts and destruction** keep P28-P31 unchanged. Reply authority
dies with every **terminal** path of its server thread, and its caller is
woken with `T_EDEAD`. The terminal paths are exactly:
- destruction (its last Thread capability is deleted)
- suspension (`thread_suspend`)
- `exit`
- loss of a binding it cannot run without (`TS_ASPACE`, `TS_CSPACE`, T2)

All of them go through one routine, `ipc_detach()`. The audit makes this
structural: **an INACTIVE thread never holds reply authority**, so a
future path to INACTIVE that forgets to release it fails the audit.

**FAULTED is not terminal.** A server that faults, with or without a
handler, keeps its authority. Its supervisor can repair and resume it,
after which it can still reply, or stop it, which is terminal. Releasing
on a fault would also cascade: a handler that faulted while holding
another faulting thread's reply would fail that delivery, which could
release that thread's authority in turn, and so on, recursively, down a
chain of handlers (P74).

The other direction:
- a caller destroyed or suspended in BLOCKED_REPLY leaves the server
  holding a caller-gone authority
- a caller aborted while still BLOCKED_SEND loses its staged message,
  offer and call flags, like any sender (P59)

**P65. Conservation.** P55 applies to a reply exactly as to a send.
Every refused `reply` or `reply_recv` leaves every capability record,
queue, thread, staged message and offer, and the reply authority
byte-for-byte unchanged. The one exception is the senders that the
drain (phase 3) failed.

**P66. Order of results.** `call` returns when the reply arrives:
RAX = 0, RSI = the reply's info word (bits 8-9: capabilities
delivered), RDI = 0. If the call is aborted, or the server dies holding
the authority, it returns only an error (`T_EINTR`, `T_EDEAD`).

## Notifications

**P20. `signal(n)`** needs WRITE on a **badged** notification capability
(`T_EPERM` if the badge is 0). It sets exactly the badge's bits, so a
signaller can set only the bits its capability was given.
- If a thread waits, the first waiter is woken with
  `pending | badge` and `pending` becomes 0.
- Otherwise `pending |= badge`.

`signal` never blocks.

**P21. `wait(n)`** needs READ.
- If `pending ≠ 0`, it returns `pending` in RSI, sets `pending` to 0, and
  does not block.
- Otherwise the thread blocks in `BLOCKED_NOTIF`.

`poll(n)` is the same but returns 0 instead of blocking.

**P22. Coalescing and no lost bits.** A structural consequence, checked by
the tests: **a notification never has waiters and pending bits at the
same time**, because a signal that finds a waiter hands it every pending
bit.
- Signals of a bit that is already pending coalesce: they create no
  additional event. Counts are not preserved; by design, a notification
  is "something happened", not a queue.
- **No set bit is ever lost:** every bit set by `signal` is either
  delivered to exactly one waiter or poller, or remains pending until a
  later `wait` or `poll` consumes it.
- **No bit is ever consumed by anything else:** only `wait`, `poll` and the
  wake-up in P20 clear bits, and only the bits they return.

## Capability transfer

**P23. Authority for a transfer.** A message may carry capabilities only
if:
- the sender's endpoint capability has GRANT (for a reply: the caller's
  `call` was made with a GRANT capability)
- every listed capability exists in the sender's (or replying server's)
  cspace, has GRANT itself, and is copyable (not Untyped or PageTable:
  `T_EINVAL`)
- the receiver offered at least as many receive slots (`recv_count`)

**P23a. Reply-transfer authority is recorded at call time.** The reply
state that `call` creates records whether the endpoint capability the
caller invoked had GRANT (`call_grant`). A `reply` may transfer
capabilities only if `call_grant` is set. The rights of whatever
endpoint capability the server holds never substitute for it: a client
that called without GRANT cannot receive capabilities through the reply,
and a server cannot push them into such a client.

**P24. Receive slots are validated as a set:** each in range, each empty,
no duplicates.
- A receiver's slots are captured from its IPC buffer once, when it calls
  `recv`; a caller's slots are captured once, when it calls `call`.
  Range and duplicates are checked at capture (`T_EINVAL`, nothing
  changes).
- Emptiness is checked again at delivery, because another thread of the
  same task may fill a slot while the owner is blocked.

**P25. Transfer is derivation, and it is atomic.**
- Each transferred capability becomes a **CDT child** of the sender's
  capability, with the same rights and badge. The sender keeps its own,
  and revoking the sender's capability later revokes the transferred
  copy. That is delegation, explicit and revocable; nothing is duplicated
  outside the derivation tree.
- The kernel runs in two phases:
  1. **Validate** everything in P3, P23 and P24, plus the receiver's
     state.
  2. **Commit:** derive each capability, deliver the words, update the
     queues and the reply link.

  The commit phase contains no failure path: every condition derive could
  reject was checked in phase 1, and the kernel is non-preemptible, so
  nothing changes between the phases.
- If validation fails, the message is not delivered at all. No capability
  is created, no data is written, the receiver stays where it was, and
  the **sender's** syscall returns the error. A receiver's bad receive
  slots therefore cost the sender an immediate error, never a block.
- Capabilities listed by a queued sender are looked up at delivery time.
  If one was deleted meanwhile, delivery fails as a whole and the sender
  is woken with `T_EBADCAP`.

### Transfer rules (step 5.4)

These refine P23-P25 for `send`/`recv`. Reply transfer (P23a) reuses the
same plan and commit in step 5.5. They change nothing about derivation
(ADR 0002) or rendezvous (P38-P48): a transfer is N derivations that
commit in the same step as a rendezvous, or not at all.

**P49. Derivation has a check half and a commit half.** The kernel's one
derivation routine is split into a check, which reports every error
derivation can give, and a commit, which has no failure path. Ordinary
derivation is check then commit, so its behaviour is unchanged. Transfer
runs every check before the first commit.

**P50. Capture.** `send` captures the slot numbers `caps[0..ncaps)` with
the words; the staged slots beyond `ncaps` are zero. `recv` captures its
offer, `recv_count` and `recv_slots[0..recv_count)`, into its TCB and
validates it at once, before it looks at any sender:
- `recv_count` > 3, or the buffer's `reserved` word nonzero: `T_EINVAL`
- an offered slot out of range, or offered twice: `T_EINVAL`
- an offered slot occupied: `T_EBUSY`

**Error codes are deliberate and part of the ABI.** A slot the
*receiver* offers that does not exist is a malformed offer: `T_EINVAL`.
A slot the *sender* names that does not exist is an out-of-range
capability address, the same `T_ERANGE` every capability lookup gives.
The two must not be unified later.

A staged offer exists only while its thread is BLOCKED_RECV, just as a
staged message exists only while BLOCKED_SEND (P42).

**P51. The sender's authority.** A message with capabilities needs GRANT
on the endpoint capability used to send it (`T_EPERM`). That is the
authority of the operation, so it is checked once, at `send`, as
`call_grant` is for a `call` (P23a); deleting that capability later does
not cancel a staged send (P43). Each listed slot must pass the
derivation check (P49) with the default mask and no new badge:
- empty slot: `T_EBADCAP`; out of range: `T_ERANGE`
- Untyped or PageTable: `T_EINVAL`
- no GRANT on the capability: `T_EPERM`

The same slot may be listed twice: that is two derivations. The checks
run at `send` and again at delivery, against whatever the sender's
cspace then holds in those slots (P25).

**P52. Fit.** Capabilities `caps[i]` go into `recv_slots[i]`, for i <
`ncaps`. A message fits a receiver if `ncaps` ≤ `recv_count` and each of
`recv_slots[0..ncaps)` is still empty at delivery (P24). A receiver that
offers no slots accepts no capabilities. Too many capabilities:
`T_EINVAL`. An occupied slot: `T_EBUSY`.

**P53. Who is charged.** Each operation runs check-everything,
then-commit (P47):
- A running `send` that meets a queued receiver gets every error
  itself: its own capabilities, fit, or a receive slot the receiver's
  task filled since the offer. The receiver stays blocked, unchanged
  (P25).
- A running `recv` gets the errors of its own offer (P50), and the
  queues are untouched.
- A queued sender whose message no longer validates (a listed
  capability gone or changed, or it does not fit this receiver's offer)
  is removed and woken with that error, and the receiver goes on to the
  next queued sender. A sender can therefore never wedge a receiver.
  This is one of the two named queue-draining operations of P37: a
  single `recv` does work proportional to the senders it fails. Each
  queued sender is failed at most once (I-E2), so in total that work is
  paid for by the senders' own `send` calls. It becomes preemptible in
  step 6.

**P54. Commit.** In one step with no failure path: derive each
capability (a CDT child of its source with the same type, object,
rights and badge, and no mapping), deliver the words, set RSI to the
info word with bits 8-9 equal to the number delivered (all or nothing,
so equal to `ncaps`), set RDI to 0 (endpoint badges are not part of this
step), and wake the partner. The receiver knows its new capabilities are
in `recv_slots[0..n)`, in order. Nothing else in its buffer is written.

**P55. Conservation.** For a transfer of N capabilities:
- **Success:** every source remains unchanged; exactly N destination
  records appear, in the offered slots, each a CDT child of its source;
  with those N skipped, the CDT order is exactly what it was; no other
  record changes.
- **Failure:** every capability record, CDT link and cspace slot,
  every queue, thread state and staged message, and the endpoint are
  byte-for-byte what they were, except for the failed queued sender of
  P53, which leaves its queue with its error.

**P56. No intermediate state.** No observer can see some capabilities
transferred and the rest not, or capabilities transferred without the
words and the wake-up. The kernel is non-preemptible between check and
commit, and commit cannot fail.

## Liveness when objects or peers disappear

**P26. Endpoint destruction.** When an endpoint's last capability is
deleted, its finaliser wakes every queued thread:
- threads in a syscall get `T_EDEAD`
- threads delivering a fault become FAULTED (P34)

The queues are then empty, before the memory can be reused (O10).

**P27. Loss of the opposite authority.** The endpoint counts the
capabilities with WRITE and with READ.

**P27a. What the counts mean.** The send count is exactly the number of
live capability records, in any cspace, CNode, thread binding slot or
other kernel-held slot, that refer to the endpoint and carry WRITE. The
receive count is the same for READ. For a notification, the signal count
is the number of live records carrying WRITE, badged or not, because an
unbadged WRITE capability can still mint signallers. These are not
counts of tasks, owners or derivation roots, and re-parenting in the CDT
(deleting a middle capability) changes none of them.

*Amended by ADR 0010 (SC17-SC19a), implemented at its stage 2:* counts
are **maintained** in the object, updated in the same commit as every
record change, and the tests compare them with an independent rescan
(`meta_audit()`) after every audited step. The paragraph below describes
the step 5 implementation that this replaced.

**How** a count is obtained is an implementation detail. In the first
implementation it is **computed, not cached**: the kernel walks the
object's own capability records, which the CDT keeps adjacent by
construction (one root per object from retype; every copy a
descendant). The tests compute the same count independently, by scanning
every capability table involved, and compare the two after every
capability mutation. If the walk ever becomes too expensive, a cached
count must itself become audited derived state. The counts are updated when
capabilities are created (retype, derive, transfer, binding) and in the
per-capability cleanup when they are deleted.
- When the last capability with **READ** disappears, every thread in the
  send queue is woken with `T_EDEAD` (or FAULTED), and later sends fail
  immediately with `T_EDEAD`.
- When the last capability with **WRITE** disappears, every thread in the
  receive queue is woken with `T_EDEAD`, and later receives fail.

The same applies to notifications: when the last capability with WRITE
on a notification is deleted, its waiters are woken with `T_EDEAD` and
later waits fail. When IRQs are bound to notifications (later), the
binding holds a kernel-held capability copy, so it counts.

**Invariant I-L1:** no thread remains blocked on an endpoint or
notification on which the operation it waits for can no longer happen. Kernel-held copies (a fault
endpoint binding) count as capabilities, because they can still deliver.

**P28. Server death with reply authority held.** When the server thread
is destroyed or suspended, or its call is aborted, the caller in
`BLOCKED_REPLY` is woken with `T_EDEAD` (a fault-delivering caller
becomes FAULTED). Both reply links are cleared.

**P29. Caller death with a reply outstanding.** When the caller is
destroyed or suspended, the server's reply authority is marked "caller
gone"; the server's next `reply` returns `T_EDEAD` (P18). No link to the
dead TCB remains.

**P30. Aborts.** Suspending a blocked thread, or losing a required
binding (T2) or its IPC buffer while one is needed, removes it from its
queue or reply link (applying P28/P29 to its peer) and leaves it
INACTIVE. When it is resumed, its interrupted syscall returns `T_EINTR`.

**P31. Destroying a blocked thread** removes it from every queue and
reply link before its memory can be reused (O10), applying P28/P29.
Queues therefore never contain stale TCB pointers.

## Fault IPC

**P32. A user fault becomes a `call` on the thread's fault endpoint.**
`TS_FAULT` must hold an endpoint capability with WRITE. The message has:
- label `FAULT_LABEL`
- four words: vector, error code, fault address, faulting RIP
- no capabilities

These values come only from the faulting thread's own state, with no
kernel pointers (a fault address is the address the thread itself tried
to use). The faulting thread is `BLOCKED_SEND` and then `BLOCKED_REPLY`
like any caller. The handler learns which thread faulted from the badge
of the fault endpoint capability bound to it, so bind distinct badges
per thread.

**P33. The handler acts only with authority.**
- Its reply decides what happens next: label 0 resumes the thread (it
  retries the faulting instruction, through IRETQ); any other label
  leaves it FAULTED.
- To change the thread's registers first, for example to skip the
  instruction, the handler needs that thread's Thread capability with
  WRITE (T3).
- Holding the fault endpoint grants **no** control over the faulting
  thread.

**P34. No handler, or the handler is gone.**
- With no fault endpoint bound, the thread becomes FAULTED, as in step 4.
- If the endpoint is destroyed, loses its last READ capability, or the
  handler dies holding the reply, the faulting thread becomes FAULTED
  (it cannot receive `T_EDEAD`: it is not in a syscall).

In every case the fault record stays readable through the Thread
capability.

**P35. Recursive faults.** Fault delivery is queueing and a state change.
It never runs handler code in kernel context and never recurses. If a
handler itself faults, its fault goes to *its* fault endpoint like any
other. If that endpoint is one only the handler serves, the threads
involved wait for each other; the kernel is unaffected, and a supervisor
holding their Thread capabilities can suspend or destroy them.

### Fault delivery contract (step 5.6)

These refine P32-P35. They freeze the user-visible ABI of a fault
message before any fault IPC is implemented. Fault delivery adds almost
no IPC machinery: the kernel constructs one controlled `call` on the
thread's behalf, and these rules constrain what can be done with it.

**P67. Which events become fault messages.** Exactly the CPU exceptions,
vectors 0-31, raised while the thread runs in ring 3. Excluded, by
construction:
- **NMI (2), #DF (8), #MC (18)** enter through the paranoid path and
  never reach the user-entry code. The fault path asserts this.
- **Faults in kernel mode never become fault messages.** A fault in
  `copy_from_user`/`copy_to_user` is fixed up into `T_EFAULT` for the
  syscall (T26, T35); any other kernel-mode fault panics.
- **State the kernel finds invalid on the way back to user mode**
  (`VEC_BAD_STATE`, T17) makes the thread FAULTED directly, with no
  message.
- **Interrupts** are not faults.

**P68. The fault message (frozen ABI).** As delivered to the handler:

| Register / word | Content |
|---|---|
| RSI (info) | label `FAULT_LABEL` (0xFFFFFFFF); length 6; no capabilities; **bit 11 set** |
| RDI | badge of the thread's `TS_FAULT` capability |
| word 0 | vector |
| word 1 | hardware error code, 0 for vectors without one |
| word 2 | fault address: CR2 for #PF, otherwise 0 |
| word 3 | RIP: where the thread resumes if resumed unchanged. For faults, the faulting instruction; for traps (#BP, #OF), the next one |
| word 4 | RSP |
| word 5 | RFLAGS, user-visible bits only (`RFLAGS_USER_MASK`) |

- **Bit 11 of the info word marks a kernel-generated fault message.** No
  thread can set it: bits 8-31 of an info word must be zero on input
  (P3). It is unforgeable even when the label is not.
- **Deliberately not transmitted:** the other general registers, FPU
  and vector state, the FS/GS bases, CS/SS (always the user selectors),
  and any kernel state. A handler that needs them reads them with the
  thread's Thread capability (READ).
- **No kernel pointers.** Every word is a value the thread itself
  produced, or a constant. The fault address is the address the thread
  itself tried to use, even if that lies in the kernel half.

**P69. Delivery is a `call` from the `TS_FAULT` binding.**
- It needs WRITE on that capability; without one, the thread becomes
  FAULTED (no handler).
- The badge comes from that capability. `call_grant` is always clear and
  the offer is always empty, **whatever rights the capability carries**.
  So a fault reply can never carry capabilities (`T_EPERM`), and its
  length must be 0 (`T_EINVAL`). The faulting thread is not in a
  syscall, and its IPC buffer is never written.
- Liveness: with no receiver waiting and no capability with READ, the
  thread becomes FAULTED at once.
- Otherwise it rendezvouses or queues like any caller (P58), flagged as
  a fault call. A queued fault call carries no capabilities, so the
  drain of P53 never fails it.

**P70. The kernel writes none of the faulting thread's registers,** at
the fault, while the fault is delivered, or on any outcome. RAX is not
set: the thread is not in a syscall. Only a holder of its Thread
capability with WRITE can change its registers (`thread_write_regs`, T3).

**P71. The reply decides.** The authority is consumed either way.
- Label 0: the thread becomes RUNNABLE and resumes through IRETQ at its
  saved RIP with its saved registers, as possibly changed by a Thread
  capability holder. Its fault record is cleared.
- Any other label: the thread becomes FAULTED and keeps its fault
  record.

**P72. Failed delivery.** The thread becomes FAULTED, and never gets an
error in a register, if:
- the endpoint is destroyed while it is queued
- the endpoint's last READ capability is deleted while it is queued
- the handler is destroyed, suspended or exits holding the reply

If the faulting thread itself is suspended while delivering, it becomes
INACTIVE with its registers untouched. If it is resumed later, it
re-executes the faulting instruction: it faults again and delivers anew.

**P73. Fault record lifetime.** The record is written at the fault and
readable with the Thread capability (READ). It is cleared when the
thread is resumed, by a label-0 reply or by `thread_resume`. A record
therefore never describes an older fault than the latest one, and a
running thread has none.

**P74. No recursion, and the self-fault rule** (an explicit state-machine
rule, not a guard):
- **Delivery cannot recurse.** It runs no handler code, touches no user
  virtual address, and cannot itself fault.
- **A thread is never the receiver of its own fault.** The faulting
  thread is the caller of its fault message, and a thread is in exactly
  one state, so it cannot also be BLOCKED_RECV. A handler whose own
  `TS_FAULT` endpoint is the one it serves therefore queues its own
  fault there and waits for another receiver. Only threads that depend
  on it are affected; a supervisor holding their Thread capabilities can
  suspend or destroy them.
- **A fault while delivering a fault is impossible:** the thread is
  blocked.
- **No cascade.** A handler that faults keeps any reply authority it
  holds (P64), so a failed delivery never turns into another thread's
  failure.

**P75. What the handler can do.** The fault endpoint and the reply
authority let a handler do exactly two things: read the six words, and
choose between resuming and leaving FAULTED. Anything else, such as
changing registers, reading other state, or suspending the thread,
needs the Thread capability.

**P76. Invariants.**
- A fault call is flagged as one in the faulting thread's TCB while
  queued, and in the server's reply flags once received. It never has
  an offer or `call_grant`.
- The audit checks these, and that a FAULTED thread is in no queue and
  no reply link as a caller.

## Atomicity (headline property)

**P36. Invariant I-A1: an IPC operation either commits completely or
returns an error with no externally observable change.** That covers
every cspace, CDT link, queue, thread state, IPC buffer, reply link and
notification word. It applies to:
- capability transfer (P25)
- creating reply authority (it is set in the same commit as delivery)
- inserting into a queue (only after every check has passed)
- blocking a sender (its message is staged and validated first)
- a failed `reply` (changes nothing but consuming its own authority, P17)

## Bounds (denial of service)

**P37.** *Amended by ADR 0010 (SC26):* the two queue-draining exceptions
below are bounded: wake-all through the reaper (SC23, SC24), the receive
drain as a thread continuation (SC25). Per-entry work is bounded by W.
- **Message size:** at most 32 words and 3 capabilities; captured into a
  fixed TCB area.
- **Queue depth:** bounded by the number of thread objects, each in at
  most one queue. A task can lengthen a queue only with its own threads,
  paid for from its own Untyped.
- **Work per operation:** each IPC operation has bounded work, O(1)
  queue operations, at most 32 words copied and 3 derivations, **except
  the queue-draining operations this ADR names explicitly.** There are
  exactly two:
  1. Endpoint or notification destruction and authority loss (P26,
     P27) wake every waiter: O(waiters).
  2. Endpoint receive (P53) may inspect and fail queued senders until
     it finds the first deliverable one: O(failed senders) plus one
     rendezvous. Each failed sender is removed exactly once (I-E2).

  A single such operation is therefore not bounded by a constant, only
  by the number of threads queued, which the queue-depth bound above
  limits. Like revocation, both become preemptible in step 6. Any new
  queue-draining path must be added to this list.
- **No allocation and no recursion.** IPC performs no user-virtual-address
  dereferences; IPC-buffer access goes only through a bound frame's
  physical address (P4, P5).
- **A server never has to block on a client:** `reply` never blocks, so
  an untrusted client cannot stall a server that only uses `recv`,
  `reply` and `reply_recv`.

## Invariants introduced

| ID | Invariant | Rules |
|---|---|---|
| I-A1 | IPC is atomic: commit completely or no observable change | P25, P36 |
| I-T1 | Capabilities move only with GRANT on the endpoint and on each capability (for a reply: the `call_grant` recorded at call time), into validated empty slots the receiver offered; each transfer is a CDT child of the sender's capability | P23–P25, P23a |
| I-R1 | Reply authority is single-use, non-transferable, and can answer only its own caller | P16–P19 |
| I-S1 | Thread states and queues always satisfy P9; a blocked thread is never runnable | P9, P10 |
| I-L1 | No thread stays blocked on an operation that can no longer happen; no queue or link refers to a dead object; the endpoint and notification capability counts always equal the live rights-bearing records | P26–P31, P27a |
| I-N1 | A set notification bit is either delivered to exactly one waiter/poller or stays pending until one consumes it; repeated signals of a pending bit coalesce; bits are consumed only by `wait`/`poll`; a signaller sets only its badge's bits | P20–P22 |
| I-F1 | Fault messages carry only the faulting thread's own state; a handler controls a thread only through its Thread capability; fault delivery never recurses | P32–P35 |
| I-B1 | IPC work, message size and queue depth are bounded; IPC never allocates and performs no user-virtual-address dereferences | P2–P6, P37 |
| I-W1 | An IPC buffer counts as a writable alias for W^X | P5 |
| I-E2 | A queued sender leaves BLOCKED_SEND with an error at most once: queue-discard work cannot charge the same sender twice | P37, P53 |
| I-C1 | Transfer conservation: a successful transfer of N capabilities adds exactly N records, each a CDT child of its source, and changes nothing else; a failed one changes nothing | P49-P56 |
| I-E1 | Endpoint rendezvous: never both queues non-empty; FIFO on each side; exactly one sender and one receiver per rendezvous; no message survives its send wait; validation before any dequeue | P38-P48 |

## Tests required before step 5 is done

All from ring 3 where the behaviour is user-visible, with the P9 audit
after every step.

1. **Rendezvous both ways:** send-then-recv and recv-then-send. Call/reply
   round trips. FIFO order with three senders and with three receivers.
2. **Message format:** 0, 1 and 32 words; label and badge delivered;
   reserved info bits, length 33 and 4 capabilities rejected; words
   beyond the length never written to the receiver; the staging area
   zero-filled.
3. **Single capture:**
   - a second thread rewrites the sender's IPC buffer while the sender is
     blocked; the receiver gets the original message
   - unbinding the sender's IPC buffer after the message is staged but
     before rendezvous: delivery still succeeds (P6a)
   - a second thread fills a receiver's offered slot while it is blocked:
     delivery of a capability fails with no change (P24)
4. **Capability transfer:** 1 and 3 capabilities, each a CDT child;
   revoking the sender's capability revokes the receiver's copy.
5. **Transfer failures, each leaving every cspace, queue and state
   unchanged** (checked by snapshotting all of them before and after):
   - endpoint without GRANT; capability without GRANT
   - Untyped or PageTable listed
   - receive slot occupied, out of range or duplicated
   - receiver offering too few slots
   - the third of three capabilities invalid, so the first two must not
     have been derived (rollback)
   - a queued sender's capability deleted before delivery
6. **Reply authority and reply transfer:**
   - a client that called without GRANT cannot receive capabilities in
     the reply, even if the server's own endpoint capability has GRANT
     (P23a)
   - a reply that fails validation keeps the authority; a later
     zero-length reply succeeds
   - `reply_recv` whose receive half is invalid delivers no reply and
     keeps the authority (P19)
   - a second `recv` while holding one fails
   - `reply` without authority fails
   - reply after the caller is destroyed or suspended returns `T_EDEAD`
   - a server destroyed holding the reply wakes the caller with `T_EDEAD`
   - reply authority can never be named as a capability
7. **Liveness:**
   - an endpoint destroyed with queued senders and receivers
   - the last READ capability deleted with senders queued
   - the last WRITE capability deleted with receivers queued
   - a blocked thread destroyed, and suspended (`T_EINTR` on resume)
   - IPC buffer unbound while receiving

   In all of these, the P9 audit finds no stale pointer.
8. **Notifications:**
   - signal before wait, and wait before signal
   - coalescing of repeated bits
   - two badges ORed together
   - `poll` empty and non-empty
   - an unbadged signal refused
   - a wait woken by exactly one signal, with no bit lost or left behind
   - destruction with waiters; the last signalling capability deleted
     with waiters
9. **Fault IPC:**
   - a fault delivered to a handler, with the correct snapshot and no
     kernel address
   - the handler fixes the thread through its Thread capability and
     resumes it
   - a handler without the Thread capability cannot change it
   - no handler; the handler gone while the fault is queued; the handler
     dies holding the reply
   - a handler that faults to itself (only those threads stall)
10. **Authority conservation, after every IPC operation in every test:**
    snapshot every capability record and CDT edge, every queue, every
    thread state, every notification word, and the endpoint counts.
    - Successful transfer of N capabilities: every source remains, exactly
      N destination records appear, exactly N CDT edges appear (each child
      of its source), and nothing else changes.
    - Any failure: everything identical to the snapshot.
    - Counts equal a full rescan (P27a) after every capability creation,
      deletion and re-parenting.
11. **Bounds:** a 1000-deep send queue of threads drained in order, with
    stack high-water marks within budget.
12. **W^X for IPC buffers:**
    - binding a frame mapped RX fails
    - mapping a bound IPC buffer RX fails

### Planned mutants

Each must be caught; one that isn't means strengthening the invariant,
not just the test:
- transfer without GRANT on the endpoint, or on the capability
- transfer into an occupied, out-of-range or duplicated slot
- commit before validating all capabilities (partial transfer)
- no rollback when the third capability is invalid
- a transferred capability not linked as a CDT child
- `call_grant` not recorded, so a reply can smuggle capabilities to a
  client that called without GRANT
- `reply_recv` committing the reply before validating the receive half
- a reply that fails validation still consuming the reply authority
- the endpoint counts not adjusted when a middle capability is deleted
  and its children re-parented
- a sender aborted when its IPC buffer is unbound after staging
- a second reply authority created, or reply not single-use
- `reply` delivering to anything other than the linked caller
- reply link not cleared when the caller is destroyed
- waiter not removed when its thread is destroyed
- endpoint destruction leaving a waiter blocked
- the READ/WRITE capability counts not updated on transfer or binding
- a notification bit lost on wake-up, or cleared without being returned
- `signal` setting bits other than the badge
- a sender left runnable while queued, or a receiver queued while runnable
- wake-up without writing the result registers, or without enqueuing
- a fault message containing a kernel address
- a fault handler controlling the thread without its Thread capability
- an IPC buffer alias allowing W^X violation
- delivery reading the sender's IPC buffer at delivery time instead of
  the staged copy

## Implementation order

1. Thread state, wait links and the P9 audit; the `T_EDEAD`/`T_EINTR`
   abort paths (no IPC yet).
2. Notifications (no capability transfer): the smallest state machine.
3. Endpoints: send/recv/call/reply/reply_recv without capabilities;
   reply authority; liveness rules.
4. Capability transfer with two-phase commit; the IPC buffer as a W^X
   alias.
5. Fault IPC.
6. Mutation testing, security review, documentation.

## Implementation notes

- **Step 5.6** (fault IPC) is implemented with P67-P76. The kernel
  builds one call from the thread's own state, then uses the ordinary
  rendezvous, reply-link and reply code. The only new behaviour is in
  `thread_wake()` and `ipc_detach()`: a thread delivering a fault gets
  no register written, and a failed delivery makes it FAULTED instead of
  returning an error.
  - Two changes came out of this step. `thread_resume` now refuses
    blocked threads: it used to make a queued thread RUNNABLE while it
    was still in its queue, a step 5.1 bug found while reading the code
    for this step. And the audit now enforces that an INACTIVE thread
    holds no reply authority (P64). Two 5.1-era tests built exactly that
    state by hand; their servers are now parked (blocked) instead of
    stopped.
  - Mutation testing: 20 mutants, all killed. Two first survived because
    the test data happened to coincide with the mutation: the handler
    and the faulting thread had the same stack top, and the faulting
    thread's RAX was already the value a mutant wrote. The test now gives
    the thread distinctive registers.
  - **Not testable under QEMU:** NMI, #DF and #MC from ring 3 (they
    take the paranoid path, asserted in the fault path), and a fault
    during IPC-buffer access, which cannot happen because IPC touches
    no user virtual address. `scripts/check-stac.sh` keeps user-memory
    access confined to the copy routines.
- **Step 5.5** (call, reply, `reply_recv`, endpoint badges) is
  implemented with P57-P66, reusing the plan and commit of P49-P56 for
  replies.
  - Staged IPC state is now erased in one place, whenever a thread
    leaves IPC (wake-up, abort, destruction). A caller's move to
    BLOCKED_REPLY keeps only its offer.
  - `exit` now releases reply authority like suspension. Without that,
    a caller could wait forever on a server that had exited.
  - Mutation testing: 20 mutants, all killed. Two first survived:
    `call_grant` not recorded when the server was already waiting
    (only the other arrival order was tested without GRANT), and the
    caller's offer never validated (no test made a call with a bad
    offer). Both now have tests.
- **Step 5.4** (capability transfer on `send`/`recv`) is implemented
  with P49-P56. Derivation was split into `cap_derive_check()` and
  `cap_derive_commit()`; ordinary derivation is check then commit, and
  commit asserts that its check still passes, so a transfer plan that
  skipped a check panics instead of committing. A receiver's offer is
  staged in its TCB like a sender's message, and the audit enforces
  both. Endpoint badges in RDI (P8) are still 0 and arrive with
  call/reply. Mutation testing: 31 mutants, all killed (three of them against the queue drain of P53). Two of them
  first survived only because every refusal test had a receiver
  waiting, where delivery re-runs the full check. A sender with nobody
  waiting could then block on a capability it can never give, so tests
  now refuse those at once from ring 3. A third survived because no
  test had junk past `ncaps` in the sender's buffer.
- **Step 5.3** (endpoint rendezvous, data words only) is implemented
  with P38-P48. P5 (an IPC buffer is a writable alias) moved forward
  into this step, because 5.3 is the first time the kernel writes into
  an IPC buffer: binding one needs READ and WRITE and no executable
  alias, and it blocks later executable mappings of the frame. On
  endpoints, the finaliser asserts that both queues are already empty:
  the final capability's cleanup hook always runs first and held
  whatever authority remained, so P43/P44 drained them. Its own wakes
  are defence in depth. Two mutants are equivalent by construction:
  dropping that wake (see above), and dropping the zeroing in capture
  (the audit proves the TCB copy is already zero, and the words of the
  local copy past the length are never read).
- **Step 5.1** (state machinery) and **step 5.2** (notifications) are
  implemented. The notification `signal` syscall takes no bits argument
  at all, so a caller cannot even express "signal these bits".
