# ADR 0009: IPC: endpoints, call/reply, notifications, capability transfer, fault IPC

Status: proposed

Refines ADR 0003, step 5. This is the specification; nothing in step 5 is
implemented until it is agreed. Rule numbers (P1..P37) are referenced from
`docs/SECURITY.md`.

IPC is where authority starts to move between tasks. Every rule below
serves one of three goals:

1. **No authority appears or moves without explicit permission**, and none
   is duplicated by accident.
2. **Every operation is atomic:** it commits completely or changes nothing
   observable.
3. **No thread is ever blocked on, or linked to, something that no longer
   exists**, and no structure ever points at a dead thread.

## Scope

In scope, and nothing else:
- synchronous endpoints: `send`, `call`, `recv`, `reply`, `reply_recv`
- notifications: `signal`, `wait`, `poll`
- capability transfer in messages
- fault delivery to a handler endpoint
- the thread states and queues these need

Explicitly **out of scope** for this step:
- **Asynchronous message queues of any kind.** The only buffering in the
  kernel is the single message staged in each blocked sender's own TCB.
- Non-blocking send variants, timeouts, and a direct-switch fast path.
  These are performance features to add after measurement.
- Unwrapping badged endpoint capabilities sent to their own endpoint
  (ADR 0003). Until then, a server that receives a copy of its own badged
  capability identifies it with `cap_identify`.
- Moving (rather than copying) capabilities, and reply objects that a
  server can hand to another thread (needed for deferred replies; MCS-
  style, later).
- Priorities and timer preemption (step 6). **T36 still gates untrusted
  code.**

## Objects

| Object | Size | Contents (kernel memory, never user-visible) |
|---|---|---|
| `Endpoint` | 64 B (exists) | send queue (head, tail), receive queue (head, tail), count of capabilities with SEND, count with RECV |
| `Notification` | 64 B (new) | pending bit word, wait queue (head, tail), count of capabilities with WRITE |

Both are retyped from Untyped like everything else (O3). Queues are
intrusive: every thread has **one** wait link in its TCB, because a thread
blocks on at most one object at a time. **IPC never allocates.**

## Rights

| Capability | Right | Allows |
|---|---|---|
| Endpoint | WRITE ("send") | `send`, `call` |
| Endpoint | READ ("receive") | `recv`, `reply_recv` |
| Endpoint | GRANT | transferring capabilities in a message sent with this capability, and receiving capabilities in the reply to a `call` made with it |
| Notification | WRITE | `signal` |
| Notification | READ | `wait`, `poll` |

**P1. Badges.** Endpoint and notification capabilities may carry a badge,
set once at derivation (as today for endpoints). A receiver learns the
badge of the capability the sender used. A notification signal sets
exactly the bits of the badge of the capability used (P20).

## Message format

**P2. A message is:**
- a 32-bit label
- up to `MSG_MAX_WORDS` = **32** data words (256 bytes)
- up to `MSG_MAX_CAPS` = **3** capability slots

**P3. The info word** carries the shape of a message in a register:

| Bits | Field |
|---|---|
| 0–5 | length in words (0..32) |
| 6–7 | number of capabilities (0..3) |
| 8–31 | must be zero on input; on output, bits 8–9 report capabilities delivered and bit 10 reports a skipped reply (P19) |
| 32–63 | label |

Reserved bits set, length > 32 or more than 3 capabilities: `T_EINVAL`.

**P4. Data and capability slots travel in the thread's IPC buffer,** a
Frame bound in `TS_IPCBUF`. The kernel reads and writes it through the
frame's physical address, never through a user pointer, so IPC
dereferences no user pointer at all.

A buffer is required to send (or reply with) any data words or
capabilities, and to receive at all. A message with length 0 and no
capabilities (label and badge only) can be sent without one. Missing
buffer: `T_EINVAL`.

```c

struct ipc_buffer {               /* fixed layout, no padding */
    uint64_t words[32];           /* message data */
    uint32_t caps[3];             /* send: slots of capabilities to transfer */
    uint32_t recv_slots[3];       /* receive: empty slots for incoming caps */
    uint32_t recv_count;          /* how many recv_slots are offered (0..3) */
    uint32_t reserved;            /* must be zero */
};
```

**P5. An IPC buffer is a writable alias.** Because the kernel writes into
it, binding a Frame as an IPC buffer counts as a writable mapping for
the W^X alias rule (ADR 0007, V6):
- binding fails if the frame is mapped executable anywhere
- mapping it executable fails while it is bound

Binding requires READ and WRITE on the frame capability, besides GRANT
(T1).

**P6. Messages are captured once, at send time.** The sender's label,
length, data words and capability slot numbers are copied from its IPC
buffer into a staging area in its own TCB when it sends, and are validated
there (T21/T27 for IPC). Nothing is read from the sender's IPC buffer
afterwards. A blocked sender's message therefore cannot change while it
waits, even if another thread writes to the buffer.

**P7. Messages carry no kernel pointers.** What a receiver gets:
- the label and data words, exactly as the sender wrote them
- the badge of the sender's capability
- the receive slots its new capabilities landed in

Kernel structures never enter a message. The staging area is zero-filled
beyond the message length, so no stale data from earlier messages leaks.

**P8. Delivery.**
- The receiver's IPC buffer gets `words[0..length)`.
- RSI gets the info word (bits 8–9: capabilities delivered).
- RDI gets the badge.
- RAX gets 0.

The rest of the IPC buffer is not touched. This extends T20: IPC syscalls
return values in RSI and RDI in addition to RAX.

## Thread states and queues

New states, added to those of ADR 0008:

| State | Where the thread is | Waiting for |
|---|---|---|
| `BLOCKED_SEND` | an endpoint's send queue | a receiver (`send`, `call`, or fault delivery) |
| `BLOCKED_RECV` | an endpoint's receive queue | a sender |
| `BLOCKED_REPLY` | no queue; linked to exactly one server thread | that server's reply |
| `BLOCKED_NOTIF` | a notification's wait queue | a signal |

**P9. Structural invariants**, checked by an audit function after every
IPC test step:
1. A thread is on the run queue **iff** it is RUNNABLE.
2. It is on an endpoint queue **iff** it is `BLOCKED_SEND` or `BLOCKED_RECV`
   on that endpoint, and in the queue matching its state.
3. It is on a notification queue **iff** it is `BLOCKED_NOTIF` on it.
4. It is `BLOCKED_REPLY` **iff** exactly one server thread's reply link
   points to it and its own link points back.
5. A thread is on at most one queue of any kind.
6. A thread is RUNNING **iff** it is the CPU's current thread.
7. Every queue link, reply link and wait-object pointer refers to a live
   object; queues are well-formed doubly linked lists.

**P10. Blocked means not runnable.** Every transition into a BLOCKED
state removes the thread from the run queue (it was RUNNING, so it is not
on it) and makes it non-current before the syscall returns to the
scheduler. Every wake-up:
- writes the result registers (P8)
- sets the state to RUNNABLE
- appends the thread to the run queue

All three happen together. The thread was blocked inside a syscall it
entered with SYSCALL, and only RAX, RSI and RDI change, so its return path
stays as ADR 0008 T18 decided.

### Transitions

| From | Event | To | Effect |
|---|---|---|---|
| RUNNING | `send` / `call`, receiver waiting | RUNNING (`send`) or BLOCKED_REPLY (`call`) | message delivered; receiver RUNNABLE; for `call`, server's reply link set |
| RUNNING | `send` / `call`, no receiver | BLOCKED_SEND | appended to send queue (the call flag is recorded) |
| RUNNING | `recv`, sender queued | RUNNING | message delivered from the queue head; sender RUNNABLE (`send`) or BLOCKED_REPLY (`call`) |
| RUNNING | `recv`, no sender | BLOCKED_RECV | appended to receive queue |
| BLOCKED_SEND | a receiver arrives | RUNNABLE or BLOCKED_REPLY | as above |
| BLOCKED_RECV | a sender arrives | RUNNABLE | message delivered |
| BLOCKED_REPLY | the server replies | RUNNABLE | reply delivered |
| RUNNING | `wait`, no bits pending | BLOCKED_NOTIF | appended to wait queue |
| BLOCKED_NOTIF | a signal arrives | RUNNABLE | bits delivered (P21) |
| any BLOCKED | `thread_suspend`, losing a required binding (T2), or losing `TS_IPCBUF` while it is needed | INACTIVE | IPC aborted (P30); on a later resume the syscall returns `T_EINTR` |
| any BLOCKED | the object or peer is destroyed, or the last opposite-direction capability is deleted | RUNNABLE with `T_EDEAD` | P26–P29 |
| any | last Thread capability deleted | destroyed | P31 |

**P11. Queues are FIFO.** Senders are served in arrival order, and so are
receivers and notification waiters.

**P12. Who runs next.** A woken thread is appended to the run queue; the
current thread continues unless it blocked. There is no direct switch yet,
so the order is deterministic and testable.

## Endpoints

**P13. `send(ep, info)`** needs WRITE on `ep`.
- If a receiver is queued, the message is delivered (P8) and both
  continue.
- Otherwise the sender blocks in `BLOCKED_SEND` until a receiver comes.

**P14. `call(ep, info)`** needs WRITE on `ep`. It is a `send` followed,
atomically at delivery, by `BLOCKED_REPLY`. The receiving thread gets the
**reply authority** for this caller (P16).

**P15. `recv(ep)`** needs READ on `ep`, a bound IPC buffer, and **no reply
authority currently held** (`T_EBUSY` otherwise; P17).
- If a sender is queued, its staged message is delivered.
- Otherwise the receiver blocks in `BLOCKED_RECV`.

### Reply authority

**P16. Reply authority is not a capability.** It is per-thread kernel
state in the server's TCB: a link to the one caller it may answer, and
the caller's link back. It lives in no cspace and has no slot number, so
it cannot be copied, transferred, derived or confused with an endpoint
capability. `reply` takes **no target argument**: it can only answer the
server's own pending caller.

**P17. At most one outstanding reply authority per server thread.**
- A server holding one cannot `recv` (`T_EBUSY`); it must `reply` or
  `reply_recv` first.
- A caller is linked to at most one server.
- Reply authority is single-use: `reply` consumes it whether the reply is
  delivered or the caller has gone.

**P18. `reply(info)`:**
- If the caller is still `BLOCKED_REPLY`, the message is delivered to it
  (P8) and it becomes RUNNABLE.
- If the caller has been destroyed or its call aborted, `reply` returns
  `T_EDEAD` and changes nothing else.
- Without reply authority: `T_EINVAL`.

**P19. `reply_recv(ep, info)`** is `reply` (when reply authority is held)
followed by `recv`. Afterwards RAX/RSI/RDI hold the *receive's* result. If
the caller had gone, the reply part is skipped silently and bit 10 of the
returned info word reports it.

## Notifications

**P20. `signal(n)`** needs WRITE on a **badged** notification capability
(`T_EPERM` if the badge is 0). It sets exactly the badge's bits, so a
signaller can set only the bits its capability was given.
- If a thread waits, the first waiter is woken with
  `pending | badge` and `pending` becomes 0.
- Otherwise `pending |= badge`.

`signal` never blocks.

**P21. `wait(n)`** needs READ.
- If `pending ≠ 0`, it returns `pending` in RSI, sets `pending` to 0, and
  does not block.
- Otherwise the thread blocks in `BLOCKED_NOTIF`.

`poll(n)` is the same but returns 0 instead of blocking.

**P22. Coalescing and no lost bits.**
- Signals of the same bit before a wait coalesce into one bit. Counts are
  not preserved; by design, a notification is "something happened", not
  a queue.
- **No bit is ever lost:** every bit set by `signal` is observed by exactly
  one later `wait` or `poll`.
- **No bit is ever consumed by anything else:** only `wait`, `poll` and the
  wake-up in P20 clear bits, and only the bits they return.

## Capability transfer

**P23. Authority for a transfer.** A message may carry capabilities only
if:
- the sender's endpoint capability has GRANT (for a reply: the caller's
  `call` was made with a GRANT capability)
- every listed capability exists in the sender's cspace, has GRANT
  itself, and is copyable (not Untyped or PageTable: `T_EINVAL`)
- the receiver offered at least as many receive slots (`recv_count`)

**P24. Receive slots are validated as a set:** each in range, each empty,
no duplicates. Duplicates are refused when the receiver calls `recv`
(`T_EINVAL`, nothing changes).

**P25. Transfer is derivation, and it is atomic.**
- Each transferred capability becomes a **CDT child** of the sender's
  capability, with the same rights and badge. The sender keeps its own,
  and revoking the sender's capability later revokes the transferred
  copy. That is delegation, explicit and revocable; nothing is duplicated
  outside the derivation tree.
- The kernel runs in two phases:
  1. **Validate** everything in P3, P23 and P24, plus the receiver's
     state.
  2. **Commit:** derive each capability, deliver the words, update the
     queues and the reply link.

  The commit phase contains no failure path: every condition derive could
  reject was checked in phase 1, and the kernel is non-preemptible, so
  nothing changes between the phases.
- If validation fails, the message is not delivered at all. No capability
  is created, no data is written, the receiver stays where it was, and
  the **sender's** syscall returns the error. A receiver's bad receive
  slots therefore cost the sender an immediate error, never a block.
- Capabilities listed by a queued sender are looked up at delivery time.
  If one was deleted meanwhile, delivery fails as a whole and the sender
  is woken with `T_EBADCAP`.

## Liveness when objects or peers disappear

**P26. Endpoint destruction.** When an endpoint's last capability is
deleted, its finaliser wakes every queued thread:
- threads in a syscall get `T_EDEAD`
- threads delivering a fault become FAULTED (P34)

The queues are then empty, before the memory can be reused (O10).

**P27. Loss of the opposite authority.** The endpoint counts the
capabilities with WRITE and with READ. The counts are updated when
capabilities are created (retype, derive, transfer, binding) and in the
per-capability cleanup when they are deleted.
- When the last capability with **READ** disappears, every thread in the
  send queue is woken with `T_EDEAD` (or FAULTED), and later sends fail
  immediately with `T_EDEAD`.
- When the last capability with **WRITE** disappears, every thread in the
  receive queue is woken with `T_EDEAD`, and later receives fail.

The same applies to notifications: when the last capability with WRITE
on a notification is deleted, its waiters are woken with `T_EDEAD` and
later waits fail. When IRQs are bound to notifications (later), the
binding holds a kernel-held capability copy, so it counts.

**Invariant I-L1:** no thread remains blocked on an endpoint or
notification on which the operation it waits for can no longer happen. Kernel-held copies (a fault
endpoint binding) count as capabilities, because they can still deliver.

**P28. Server death with reply authority held.** When the server thread
is destroyed or suspended, or its call is aborted, the caller in
`BLOCKED_REPLY` is woken with `T_EDEAD` (a fault-delivering caller
becomes FAULTED). Both reply links are cleared.

**P29. Caller death with a reply outstanding.** When the caller is
destroyed or suspended, the server's reply authority is marked "caller
gone"; the server's next `reply` returns `T_EDEAD` (P18). No link to the
dead TCB remains.

**P30. Aborts.** Suspending a blocked thread, or losing a required
binding (T2) or its IPC buffer while one is needed, removes it from its
queue or reply link (applying P28/P29 to its peer) and leaves it
INACTIVE. When it is resumed, its interrupted syscall returns `T_EINTR`.

**P31. Destroying a blocked thread** removes it from every queue and
reply link before its memory can be reused (O10), applying P28/P29.
Queues therefore never contain stale TCB pointers.

## Fault IPC

**P32. A user fault becomes a `call` on the thread's fault endpoint.**
`TS_FAULT` must hold an endpoint capability with WRITE. The message has:
- label `FAULT_LABEL`
- four words: vector, error code, fault address, faulting RIP
- no capabilities

These values come only from the faulting thread's own state, with no
kernel pointers (a fault address is the address the thread itself tried
to use). The faulting thread is `BLOCKED_SEND` and then `BLOCKED_REPLY`
like any caller. The handler learns which thread faulted from the badge
of the fault endpoint capability bound to it, so bind distinct badges
per thread.

**P33. The handler acts only with authority.**
- Its reply decides what happens next: label 0 resumes the thread (it
  retries the faulting instruction, through IRETQ); any other label
  leaves it FAULTED.
- To change the thread's registers first, for example to skip the
  instruction, the handler needs that thread's Thread capability with
  WRITE (T3).
- Holding the fault endpoint grants **no** control over the faulting
  thread.

**P34. No handler, or the handler is gone.**
- With no fault endpoint bound, the thread becomes FAULTED, as in step 4.
- If the endpoint is destroyed, loses its last READ capability, or the
  handler dies holding the reply, the faulting thread becomes FAULTED
  (it cannot receive `T_EDEAD`: it is not in a syscall).

In every case the fault record stays readable through the Thread
capability.

**P35. Recursive faults.** Fault delivery is queueing and a state change.
It never runs handler code in kernel context and never recurses. If a
handler itself faults, its fault goes to *its* fault endpoint like any
other. If that endpoint is one only the handler serves, the threads
involved wait for each other; the kernel is unaffected, and a supervisor
holding their Thread capabilities can suspend or destroy them.

## Atomicity (headline property)

**P36. Invariant I-A1: an IPC operation either commits completely or
returns an error with no externally observable change.** That covers
every cspace, CDT link, queue, thread state, IPC buffer, reply link and
notification word. It applies to:
- capability transfer (P25)
- creating reply authority (it is set in the same commit as delivery)
- inserting into a queue (only after every check has passed)
- blocking a sender (its message is staged and validated first)
- a failed `reply` (changes nothing but consuming its own authority, P17)

## Bounds (denial of service)

**P37.**
- **Message size:** at most 32 words and 3 capabilities; captured into a
  fixed TCB area.
- **Queue depth:** bounded by the number of thread objects, each in at
  most one queue. A task can lengthen a queue only with its own threads,
  paid for from its own Untyped.
- **Work per operation:** O(1) queue operations, at most 32 words copied
  and 3 derivations. The exceptions are endpoint or notification
  destruction and authority loss (P26, P27), which wake every waiter:
  O(waiters). Like revocation, these become preemptible in step 6.
- **No allocation, no recursion, no locks held across user memory
  access** (there is no user memory access in IPC at all).
- **A server never has to block on a client:** `reply` never blocks, so
  an untrusted client cannot stall a server that only uses `recv`,
  `reply` and `reply_recv`.

## Syscalls

| Syscall | Arguments | Returns (RAX, RSI, RDI) |
|---|---|---|
| `SYS_SEND` | endpoint slot, info | status |
| `SYS_CALL` | endpoint slot, info | status, reply info, 0 |
| `SYS_RECV` | endpoint slot | status, info, badge |
| `SYS_REPLY` | info | status |
| `SYS_REPLY_RECV` | endpoint slot, info | as `SYS_RECV` |
| `SYS_SIGNAL` | notification slot | status |
| `SYS_WAIT` | notification slot | status, bits |
| `SYS_POLL` | notification slot | status, bits (0 if none) |

New errors: `T_EDEAD` (the object, or the peer or authority on the other
side, is gone) and `T_EINTR` (the operation was aborted by suspension or
binding loss).

## Invariants introduced

| ID | Invariant | Rules |
|---|---|---|
| I-A1 | IPC is atomic: commit completely or no observable change | P25, P36 |
| I-T1 | Capabilities move only with GRANT on the endpoint and on each capability, into validated empty slots the receiver offered; each transfer is a CDT child of the sender's capability | P23–P25 |
| I-R1 | Reply authority is single-use, non-transferable, and can answer only its own caller | P16–P19 |
| I-S1 | Thread states and queues always satisfy P9; a blocked thread is never runnable | P9, P10 |
| I-L1 | No thread stays blocked on an operation that can no longer happen; no queue or link refers to a dead object | P26–P31 |
| I-N1 | Notification bits are never lost and never consumed except by `wait`/`poll`; a signaller sets only its badge's bits | P20–P22 |
| I-F1 | Fault messages carry only the faulting thread's own state; a handler controls a thread only through its Thread capability; fault delivery never recurses | P32–P35 |
| I-B1 | IPC work, message size and queue depth are bounded; IPC never allocates and never touches user memory through a pointer | P2–P6, P37 |
| I-W1 | An IPC buffer counts as a writable alias for W^X | P5 |

## Tests required before step 5 is done

All from ring 3 where the behaviour is user-visible, with the P9 audit
after every step.

1. **Rendezvous both ways:** send-then-recv and recv-then-send. Call/reply
   round trips. FIFO order with three senders and with three receivers.
2. **Message format:** 0, 1 and 32 words; label and badge delivered;
   reserved info bits, length 33 and 4 capabilities rejected; words
   beyond the length never written to the receiver; the staging area
   zero-filled.
3. **Single capture:** a second thread rewrites the sender's IPC buffer
   while the sender is blocked; the receiver gets the original message.
4. **Capability transfer:** 1 and 3 capabilities, each a CDT child;
   revoking the sender's capability revokes the receiver's copy.
5. **Transfer failures, each leaving every cspace, queue and state
   unchanged** (checked by snapshotting all of them before and after):
   - endpoint without GRANT; capability without GRANT
   - Untyped or PageTable listed
   - receive slot occupied, out of range or duplicated
   - receiver offering too few slots
   - the third of three capabilities invalid, so the first two must not
     have been derived (rollback)
   - a queued sender's capability deleted before delivery
6. **Reply authority:**
   - a second `recv` while holding one fails
   - `reply` without authority fails
   - reply after the caller is destroyed or suspended returns `T_EDEAD`
   - a server destroyed holding the reply wakes the caller with `T_EDEAD`
   - reply authority can never be named as a capability
7. **Liveness:**
   - an endpoint destroyed with queued senders and receivers
   - the last READ capability deleted with senders queued
   - the last WRITE capability deleted with receivers queued
   - a blocked thread destroyed, and suspended (`T_EINTR` on resume)
   - IPC buffer unbound while receiving

   In all of these, the P9 audit finds no stale pointer.
8. **Notifications:**
   - signal before wait, and wait before signal
   - coalescing of repeated bits
   - two badges ORed together
   - `poll` empty and non-empty
   - an unbadged signal refused
   - a wait woken by exactly one signal, with no bit lost or left behind
   - destruction with waiters; the last signalling capability deleted
     with waiters
9. **Fault IPC:**
   - a fault delivered to a handler, with the correct snapshot and no
     kernel address
   - the handler fixes the thread through its Thread capability and
     resumes it
   - a handler without the Thread capability cannot change it
   - no handler; the handler gone while the fault is queued; the handler
     dies holding the reply
   - a handler that faults to itself (only those threads stall)
10. **Bounds:** a 1000-deep send queue of threads drained in order, with
    stack high-water marks within budget.
11. **W^X for IPC buffers:**
    - binding a frame mapped RX fails
    - mapping a bound IPC buffer RX fails

### Planned mutants

Each must be caught; one that isn't means strengthening the invariant,
not just the test:
- transfer without GRANT on the endpoint, or on the capability
- transfer into an occupied, out-of-range or duplicated slot
- commit before validating all capabilities (partial transfer)
- no rollback when the third capability is invalid
- a transferred capability not linked as a CDT child
- a second reply authority created, or reply not single-use
- `reply` delivering to anything other than the linked caller
- reply link not cleared when the caller is destroyed
- waiter not removed when its thread is destroyed
- endpoint destruction leaving a waiter blocked
- the READ/WRITE capability counts not updated on transfer or binding
- a notification bit lost on wake-up, or cleared without being returned
- `signal` setting bits other than the badge
- a sender left runnable while queued, or a receiver queued while runnable
- wake-up without writing the result registers, or without enqueuing
- a fault message containing a kernel address
- a fault handler controlling the thread without its Thread capability
- an IPC buffer alias allowing W^X violation
- delivery reading the sender's IPC buffer at delivery time instead of
  the staged copy

## Implementation order

1. Thread state, wait links and the P9 audit; the `T_EDEAD`/`T_EINTR`
   abort paths (no IPC yet).
2. Notifications (no capability transfer): the smallest state machine.
3. Endpoints: send/recv/call/reply/reply_recv without capabilities;
   reply authority; liveness rules.
4. Capability transfer with two-phase commit; the IPC buffer as a W^X
   alias.
5. Fault IPC.
6. Mutation testing, security review, documentation.
